# framelink measurements

Every number in the README comes from this document. Each section states the method, the setup and the expected result, then the measured result. Raw data lives in `bench/results/` as CSV, one file per run, named `<test>_<target>_<date>.csv`.

A result is only published with its methodology. If a number cannot be reproduced from the steps here, it is a bug in this document.

## Common rules

- Each result is the median of at least 5 runs. The CSV keeps every run.
- Counters come from `fl_get_stats()`, using the names in [SPEC.md](SPEC.md#8-statistics). They are never estimated from wall-clock timing.
- **Undetected corruption is measured, not assumed.** Every benchmark payload starts with a 32-bit counter and ends with a CRC-32 of the payload, generated by the bench tool. The receiving side checks both, independently of framelink. The `undetected` column in every table is the count of frames that framelink delivered but this end-to-end check rejected.

## 1. Decoder cost, cycles per byte

**Question:** how much CPU does decoding cost on a small MCU?

**Method:** the `bench` app in [ports/esp32](../ports/esp32/README.md), collected with `bench/esp32_collect.py`.

- The decoder is fed from a RAM buffer, with no UART involved, so only framelink's own work is counted.
- Cycles are counted with `esp_cpu_get_cycle_count()`, with interrupts disabled for each 1 KB chunk.
- Cost is `total_cycles / total_bytes`.
- Four 32 KB inputs:
  1. **Clean, small:** back-to-back valid frames with 16-byte payloads.
  2. **Clean, large:** back-to-back valid frames with 255-byte payloads.
  3. **Garbage:** random bytes containing no `0x7E`. This measures the HUNT state.
  4. **Worst case:** back-to-back valid headers that each announce a 255-byte payload. Each candidate fails its CRC16 only after a full frame is buffered, and the rescan finds the next header 5 bytes later, so every input byte is checked about 50 times. Random noise essentially never produces this, because it needs a valid header CRC every 5 bytes, but an attacker who controls the wire can. See [DESIGN.md](DESIGN.md#failure-modes-framelink-does-not-protect-against).
- Each input runs with the bitwise CRC (`sdkconfig.bench`) and with `FL_CRC_TABLE` (`sdkconfig.bench_table`).

**Reference point, desktop PC.** The worst case is about 60 times slower than clean input with the bitwise CRC, and 46 times slower with the table. The ESP32 numbers below decide whether it matters at a given baud rate.

### 1b. Interrupt cost per received byte

On ESP32, the UART interrupt belongs to the ESP-IDF driver, which copies bytes into a ring buffer. framelink never runs in interrupt context: `fl_poll` decodes in a normal task. Timing the driver's interrupt handler needs a custom handler, so it is not measured in v1. What framelink adds per byte is the decoder cost in section 1.

## 3. UART throughput, with and without flow control

**Question:** how close does framelink get to line rate, and what happens without credits?

**Theoretical ceiling:** UART 8N1 carries 10 bits per byte. Frame overhead is 7 bytes.

| Baud | Payload 16 B | Payload 64 B | Payload 255 B |
|------|--------------|--------------|---------------|
| 115200 | 8,014 B/s | 10,384 B/s | 11,212 B/s |
| 921600 | 64,111 B/s | 83,074 B/s | 89,698 B/s |

**Method:** the `loopback` app in [ports/esp32](../ports/esp32/README.md). UART1 and UART2 of one ESP32 are wired to each other, so both ends are real UARTs and real framelink endpoints.

- Endpoint A sends 64-byte payloads as fast as framelink allows. Endpoint B consumes frames at a fixed rate set to **50% of the ceiling**, simulating a busy receiver.
- Window 16, receive queue 4, `rto_ms` 60 at 115200 baud and 20 at 921600 baud. Each test runs for 10 seconds.
- **Flow control on:** normal operation.
- **Flow control off:** A overwrites its view of the peer's credits with 255 before every send, so it behaves like a sender that ignores back-pressure. ARQ still runs, so frames that overflow are retransmitted rather than lost.
- Goodput is unique payload bytes delivered to B's application per second.

**Expected:** with flow control, goodput sits at the consumer rate, `overflows` is zero and retransmits are near zero. Without it, `overflows` and `retransmits` grow, and the wasted line time is visible as the gap between bytes sent and goodput.

## 4. Recovery under injected corruption

**Question:** does the decoder recover, and does ARQ deliver everything, as corruption rises?

**Definition of the rate.** The corruption rate `r` is the probability that **each byte** has one randomly chosen bit flipped. It is applied independently to every byte in both directions, including ACKs. A per-byte rate of 1% corresponds to a per-bit error rate of about 0.13%.

This matters. Interpreted as a per-bit error rate, 10% would destroy essentially every frame of any useful size, and the test would measure nothing.

**Method:**

- The `noisy` proxy in `host/` sits between two endpoints and applies `r` using a fixed, logged random seed.
- Each run sends 10,000 data frames.
- Configuration: window 4, `rto_ms` 50, `max_retries` 10.
- Runs on host first, in CI, with C and Python endpoints over TCP. Then on hardware with the proxy between the Python host and the MCU UART.

**Expected results.** The probability that a frame of `L` bytes arrives intact is `(1 - r)^L`. The probability that a data frame and its 9-byte ACK both survive is `(1 - r)^(L + 9)`, which gives a pessimistic estimate of transmissions needed per delivery.

| Payload | Frame | r = 1% intact | r = 5% intact | r = 10% intact | Transmissions per delivery at 1% / 5% / 10% |
|---------|-------|---------------|---------------|----------------|---------------------------------------------|
| 16 B | 23 B | 79.4% | 30.7% | 8.9% | 1.4 / 5.2 / 29 |
| 64 B | 71 B | 49.0% | 2.6% | 0.06% | 2.2 / 61 / about 4,600 |
| 255 B | 262 B | 7.2% | ~0% | ~0% | 15 / unusable / unusable |

So the published recovery test uses **16-byte payloads**. The 64-byte row is run too, to show where the link becomes unusable. At 10% with 64-byte payloads, `max_retries` is expected to be exceeded, and those runs report link-down events instead of delivery.

**Pass criteria:**

- Zero decoder crashes or hangs.
- Zero frames delivered out of order or duplicated.
- Every frame is either delivered or reported through `on_link_down`. None disappear silently.
- `undetected` is reported as measured, even if non-zero.

## 6. Fuzzing

**Method:**

- Harness: `fuzz/fuzz_decoder.c`, built with clang and `-fsanitize=fuzzer,address,undefined`.
- Target: the decoder alone, fed byte by byte, plus a whole-link harness that drives two contexts through an adversarial channel.
- Seed corpus: the test vectors plus hand-made edge cases, committed in `fuzz/corpus/`.
- Dictionary: `fuzz/framelink.dict` with the SYNC byte and all control TYPE values.
- Additional check: the harness aborts if any single input costs more than a fixed cycle budget per byte, which turns a performance regression in rescanning into a crash.

## 7. Same-hardware comparison with MIN and TinyFrame

**Question:** are the differences claimed in the README's comparison table visible in numbers, on the same hardware and the same input?

This section is a stretch goal for v1. It is published only if all three libraries are measured under identical conditions. A comparison that is not like-for-like is worse than none.

**Method:**

- MIN and TinyFrame are vendored at the commits named in [DESIGN.md](DESIGN.md#prior-art), with their default configuration except where noted.
- TinyFrame is built with `TF_InitStatic`, a 1-byte LEN and `TF_CKSUM_CRC16`, which is the closest match to framelink's integrity check.
- MIN is built with its reliable transport enabled.
- All three run on the same ESP32 board, with the same compiler and flags, fed from the same RAM buffers as in section 1.
- **Decoder cost:** the clean and garbage inputs from section 1, re-encoded in each library's own frame format.
- **Recovery:** a fixed stream of 10,000 frames with 16-byte payloads, each library's format, with the same corruption seed applied at r = 1%, 5% and 10%. The count is of frames the decoder accepts, before any retransmission. This isolates the resync behaviour of each decoder.
- **Overload:** a receiver that consumes at 50% of line rate, as in section 3. Only MIN and framelink take part, since TinyFrame has no delivery guarantee. The count is of frames lost or retransmitted.
